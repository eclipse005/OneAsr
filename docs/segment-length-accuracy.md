# 分段长度（chunk_target_seconds）对转写精度的影响 —— 多语言实测报告

> 测试日期 2026-10-05 · 引擎 Qwen3-ASR-0.6B-hf（fp16, wgpu/Vulkan, Intel iGPU）+ ForcedAligner
> 方法与全部原始数据见 `tmp/segtest/`（复现命令在文末附录）。

## 一句话结论

**分段长度对精度有影响，但影响方式和大小高度依赖语言与音频难度：**
干净朗读音频（英德法西）在 30–180s 全档位基本无差异（WER 8.0–8.4%，波动 ≈ 噪声）；
中日粤在两端变差（30s 与 180s 各差 1.5–3.5 个百分点，60–90s 最好）；
**难音频（真实综艺人声）在 180s 档灾难性失效**——112 秒的块模型只返回 5 个字，
整段错误率从 ~43% 跳到 66%。产品默认 60s 恰好处在各语言都安全的位置。

## 实验设置

- **实验 A（端到端，产品真实路径）**：把 mini_asr_data 的短音频按固定顺序拼成每语言一条
  长音频（en 212s / zh 269s / ja 280s / yue 253s / de 624s / fr 515s / es 307s，片段间 0.5s 静音），
  外加真实视频音频 ko（266.6s，《Veiled Cup》综艺人声）。
  每条音频用 oneasr-cli 完整管线（VAD → ASR → 对齐 → 断句导出）跑
  `chunk-seconds ∈ {30, 60, 90, 120, 180}`（产品全部预设档），共 8 语言 × 5 档 = 40 格。
  打分：拉丁语系 WER、中日粤 CER（NFKC→小写→去标点；CJK 去空白）。
- **实验 B（隔离模型因素）**：同一音频用 asr-chunk 直接单次喂模型
  `[0, 15/30/60/90/120/180s/全长]`（窗口对齐拼接边界，reference 前缀精确），
  排除 VAD 切块位置的影响，看"模型一次看到的音频长度"本身的效应。
- **归因方法**：确定性贪心解码下，用 asr-chunk 按管线 plan 的**完全相同时间跨度**重放切块，
  逐例比对"模型原始输出 → 对齐词表 → 最终 TXT"三层，确定丢失发生在哪一层。

## 三个失效机制（漏词专题）

**"漏词"确实存在，但全部发生在模型层，管线（VAD/对齐/导出）没有丢过已识别的字。**
40 个格子 × 每格 20–40 个片段（约 760 次片段暴露）中，整句级丢失 6 次，
归结为三个机制，每个都有重放证据：

### 机制1：长块内整句跳过（最符合"分段越长越容易漏"的直觉）

- en 的 T-Rex 句（"They have feet with scales and claws…like a T-Rex."，6.7s 片段）：
  - 单独喂模型 → 逐字正确；
  - 位于 79s / 114s / 160s 块内（c90/c120/c180）→ **整句消失**（重放同跨度切块，模型输出里确实没有）；
  - 位于 ≤46s 块内（c30）→ 完整保留。
- ja 的「棲み分けと組み換え…シャッフル」句：33s 块内（c30）和 102s 块内（c180）都被跳过，
  单独喂 10.4s → 基本正确（仅少一个ッ）。
- **阈值因内容而异**：同一模型，en 干净语音约 60–79s 开始跳，ja 这句 33s 就跳。
- ko 整条直喂（267s 单次）WER 66.9%，与管线 c180 的 66.2% 同一失效——确认是模型层。

### 机制2：切块截断（块边界落在句中）

- en 的同一句 T-Rex 在 c60 档：切块（55.4s，静音中点）恰好落在句中，
  前半句 "They have feet with scales and claws, they lay eggs, and they" **丢失**，
  后半句 "On their two back legs, like a T. Rex." 从下一块头部恢复。
- 全局统计上这是**次要效应**：所有 40 格加权后，块边界 ±2s 内 token 错误率 9.26%，
  远离边界 9.01% —— 静音中点切块策略整体有效（例外见 ja_c60/c120 的局部集中，样本仅 16/19 个 token）。

### 机制3：重复句折叠（偶发，与块长非单调）

- FLEURS 数据集中相邻两个片段是**同一句话**（171.5s 与 183.3s 各说一遍）。
  c30 档两个副本同落在一个 29s 块里，模型只输出了一遍（重复遍丢失，21 词）；
  c60/c90/c120/c180 档都完整保留了两遍。单独看是模型对连续重复内容的去重行为，偶发。

### 各档位丢失强度（删除率 D/N）

| cell | D/N | 说明 |
|---|---|---|
| ko_c180 | **53.9%** | 112s 块 ASR 只返回 23 字符，近乎失效 |
| ko_c30–c120 | 18.8–24.7% | 难音频本底，各档接近 |
| ja_c30 / ja_c180 | 6.5% / 6.0% | 两端各丢一句 + 零星截断 |
| en_c90/120/180 | ~5.2% | T-Rex 句被跳 |
| 其余 31 格 | ≤5%，多数 0 整句丢失 | |

### ko_c180 失效探针（证据链）

- 重放失效块 [154.7s, 266.6s]（112s）→ 模型返回 **5 个字符**（"네. 네."）；
- 对半切两次（56s × 2）→ 29 + 69 字符，部分恢复（该段本身极难：快语速+多人+音乐）；
- 同一区域起点差 6 秒（210.65s vs 217.06s 起），输出 69 vs 314 字符——
  **难音频上模型输出对切块起点高度敏感（混沌），长块放大这种不稳定性**。

## 人声分离对照实验（N 卡重跑，同硬件对照）

对实验A中效果最差的 10 个格子（ko 全部 5 档、ja_c30/ja_c180、yue_c30、en_c90/en_c180），
在独显（`ONEASR_DEVICE=nvidia`）上重跑：每格先跑基线、再开 `--vocal-separation`（HTDemucs），
同硬件对比。基线与核显时代的 iGPU 结果**逐格完全一致**（跨 GPU 确定性可复现）。

| cell | 基线% | 分离% | Δ | 删除 D 基/分 | 备注 |
|---|---|---|---|---|---|
| ko_c30 | 39.61 | 39.61 | 0.00 | 30/26 | 持平 |
| ko_c60 | 43.51 | 37.01 | **-6.49** | 38/30 | 改善 |
| ko_c90 | 42.86 | 39.61 | **-3.25** | 29/23 | 改善 |
| ko_c120 | 42.86 | 42.86 | 0.00 | 31/32 | 持平 |
| ko_c180 | 66.23 | 64.94 | -1.30 | 83/85 | **崩坏未被挽救** |
| ja_c30 | 15.35 | 19.40 | **+4.05** | 61/97 | 变差 |
| ja_c180 | 16.42 | 21.54 | **+5.12** | 56/139 | **明显变差** |
| yue_c30 | 12.86 | 7.74 | **-5.12** | 2/3 | 回到 c60–c180 水平 |
| en_c90 | 10.13 | 6.03 | **-4.09** | 24/2 | T-Rex 句整句回归 |
| en_c180 | 10.13 | 6.03 | **-4.09** | 23/4 | 同上 |

**结论：人声分离不是稳定的收益，按素材决定：**

1. **有 BGM/噪声的真实音频（ko）：小幅改善**（-0～-6.5pt），方向正确但不决定性；
   **救不了 180s 长块的崩坏**（ko_c180 删除数 83→85，本质是长度问题不是混音问题）。
2. **干净朗读音频：结果两极**——en 的整句跳过被分离"治好"（删除 24→2，句子回归），
   yue_c30 的劣化消失；但 **ja 反而多丢两句**（大删除串 1→3，最长 48 字）。
   机制推测：分离+重采样改变了波形细节，把模型"洗"进了不同的解码路径——
   对"跳句"这种不稳定行为，分离是重新掷骰子，不是修复。
3. **实用建议**：默认关闭是对的；素材明显带音乐时可以开（预期小幅改善）；
   遇到"整句被跳过"时，开分离或换 chunk 档位都值得一试（都是换解码路径），
   但日语素材要复查分离后结果，本组实测开分离多丢了内容。

## 原版 Python 对照：跳句与长块失效是模型行为，不是移植问题

用 transformers 5.17 原生 `Qwen3ASRForConditionalGeneration` 直接加载同一份 -hf 权重
（conda `asr` 环境，CUDA fp16，贪心，max_new_tokens=2048 —— 与 asr-chunk 同参；
prompt 按 D:\Qwen3-ASR 仓库 `_build_text_prompt` 逐字复刻），在与 Rust 完全相同的
音频跨度上重放。注：原版仓库自带的 qwen_asr 包装层钉在 transformers 4.57.6，
与环境的 5.17 不兼容（`check_model_inputs` 装饰器 API 变更），故走原生 API；
官方离线路径对 ≤1200s 音频本来就是整段单次解码（`MAX_ASR_INPUT_SECONDS=1200`），
与我们喂整段的做法同构。

| 跨度 | 原版 vs 移植 | 关键标记（漏句句） |
|---|---|---|
| en [0, 78.8s]（c90 块） | **逐字一致** | 两者都无 "scales and claws" |
| en [0, 159.8s]（c180 块） | **逐字一致** | 两者都无 |
| en clip 单独 6.7s | **逐字一致** | 两者都有，句子完整 |
| en 整条 212.5s 单次 | **逐字一致**（WER 同 9.27%） | **整段喂原版也跳句** |
| ja 块 [178.1, 211.1] | 同长（71 字）、同跳「棲み分け」句 | 个别字符不同（風向き/風吹き） |
| ja clip 单独 10.4s | **逐字一致**（连 ッ 脱落都一致） | 都有（缺 ッ） |
| zh 整条 269.2s 单次 | **逐字一致**（CER 同 8.17%） | — |
| ja 整条 280.4s 单次 | **逐字一致**（CER 同 14.82%） | — |
| ko [217.1, 266.6] | **逐字一致**（314 字符） | — |
| ko [154.7, 266.6]（112s 崩坏块） | 双双失效，形态不同 | 原版"네. 네."复读打满 2048 token（98.7s）；移植 23 字早停 |
| ko [210.7, 266.6] | 双双失效（74.7% vs 94.2%） | 起点 →217.1 后两者逐字一致 |

**判定：**

1. **整句跳过（漏句）是模型本身在长单次输入下的行为**——官方实现在同跨度上
   连跳哪些句、连 ッ 脱落这种细节都逐字复现；整条 212.5s 直接喂原版同样跳句。
   与 wgpu 移植无关。
2. **移植数值上高度忠实**：解码稳定区两引擎输出逐字一致（fp16 CUDA PyTorch vs
   fp16 wgpu）；仅在不稳定的混沌区（ko 难音频、个别长块）出现少量分叉——
   那里的输出本来就对起点/数值扰动高度敏感，两个引擎各自"掷骰子"。
3. **ko 长块失效同样是模型行为**：原版在 112s 难块上甚至更糟（复读循环打满
   2048 token），移植的早停（23 字）反而更克制。移植无需"修"这个行为；
   产品层的缓解手段（分段调小、异常密度重切、人声分离重掷）才是正解。
4. 官方路径允许 ≤1200s 整段喂入——比产品 180s 上限激进得多；产品按 30–180s
   分段本身就是对这一模型缺陷的防护。

## 其他发现

1. **速度**：转写吞吐对块数不敏感（de：23 块与 9 块同为 28.4× 实时），
   但 **180s 长块本身慢一倍**（de_c180 12.7× vs 其余档 27–28×）——短块反而更快。
   模型加载（5–13s）主导短音频任务的耗时。
2. **后端选择（本次已实现）**：此前 `backend=auto` 固定取枚举序第一个适配器——双 GPU 机器上
   就是核显，独显永远闲置，且 CLI/engine 没有任何选择入口。本次给 oneasr-core 加了
   `ONEASR_DEVICE` 环境变量（ASR / ForcedAligner / HTDemucs 三个引擎统一支持）：
   - 语法与推理 crate 一致：`auto`（默认）| `cpu` | `vulkan:1` / `dx12` | `#1` / `1` |
     适配器名子串（如 `nvidia`，大小写不敏感）；spec 非法**直接报错**，不静默回退。
   - 本机实测（P104-100）：N 卡正常接管（utilization 74–99%，显存 2–2.9GB），
     输出与核显**逐字一致**；0.6B 转写速度两卡持平（180s 音频 8.2s，22× 实时——
     该负载瓶颈不在算力）；但 **HTDemucs 分离在 N 卡 13–30s vs 核显 84s**，收益明显。
   - 单测覆盖 spec 规整与 backend 组装；`cargo check/clippy/fmt/test -p oneasr-core` 全绿。
3. **CJK 计分的字形变异**：yue_c30 的"恶化"有相当部分是字形/数字格式翻转
   （報導↔報道、20↔二十、賈斯汀↔加斯丁、義大利↔意大利），模型按分块上下文选不同写法；
   CER 把它们计为错误，但不影响可懂度。真实听错（的↔得、五連敗↔五年霸）也存在。
4. 产品在 `时长 ≤ chunk 目标` 时**整文件单块直通且跳过 VAD**（`asr.rs` / `vad.rs`），
   因此同一档位对短文件意味着"无 VAD 全长单块"——这在本次拼接音频（都 >180s）中未覆盖，
   但实验 B 的全长直喂点近似了该行为。

## 建议

1. **默认 60s 保持不变**——所有语言的安全区；CJK 的最优区（60–90s）。
2. **拉丁语系无需调节**：30–180s 随便选，差异在噪声内（<0.5pt）。
3. **日语用户避免 30s 与 180s 两个极端**（U 形，摆幅 3.5pt 且两端都有整句丢失实例）；
   如做语言相关默认值，ja 建议 60–90s。
4. **难音频（音乐/多人/嘈杂）避免 180s**：ko 实测 180s 档直接崩坏（112s 块近空返回）。
   工程上可加一个廉价护栏：**单块转写字符密度异常低时（如 < 2 字符/秒语音）自动对半重切重试**，
   能兜住本次 ko_c180 这类失效。
5. 漏词三大机制都指向同一个方向：**块越接近模型舒适区（~30–60s）越不容易丢**，
   但 <30s 会进入截断/上下文不足的代价区——产品下限 30s 是合理的。

## 局限

- 0.6B fp16 单模型；1.7B / int8 未复测（CLI 无模型选择参数，需另行验证）。
- 朗读型语料（FLEURS/MLS）为主，ko 一条真实综艺音频；无多说话人重叠/强音乐的系统采样。
- 每格单次运行（贪心解码确定性，但 CJK 字形翻转显示解码仍受上下文微小扰动）。
- 边界分析在 zh_c60–c180 四格因词表 token 映射不一致跳过（不影响主表与丢失分析）。
- 分组均值样本小（拉丁 4 语言、CJK 3 语言），摆幅 <1pt 的差异不应过度解读。
