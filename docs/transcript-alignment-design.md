# 「文稿匹配」功能设计 —— issues #2 / #14

> 2026-10-06 · 输入：issue #2「希望增加文稿匹配功能」（已关，指向 CTC 对齐）、
> issue #14「希望增加 两个功能」（开放，ASS 部分已落地）。
> 引擎侧：`docs/ctc-aligner-adoption-analysis.md`（CTC 对齐器已并入）。
> 已有基础：时间轴边界（`crates/oneasr-core/src/timeline.rs`）、ASS 渲染器
> （`crates/oneasr-core/src/subtitle/ass.rs`）。

## 1. 需求

| 来源 | 原话要点 | 本质 |
|---|---|---|
| #2 | 「类似剪映的文稿匹配：添加音频和对应的逐字稿，给逐字稿自动打上时间戳，生成 srt」 | 音频 + 文稿 → 字幕，跳过识别 |
| #14.2 | 「识别出文字后可以修改校正，还有自己分行，然后再用 ForcedAligner 生成字幕」 | 识别 → 校对 → 重对齐 |
| #14.3 | 「如果自己本身就是文稿，就不需要识别语音……可以选择生成 srt（一行一个时间）和 ass（每个字都有时间）」 | 同 #2 + ASS（**已实现**） |
| #14.1 | 「希望能生成 ass 格式的、每个字有时间戳的字幕文件」 | ASS 逐字（**已实现**） |

收敛为**一个新能力**：一条任务可以挂一份文稿，挂了就跳过识别、只做打轴。

### 1.1 为什么 CTC 对齐器是这个功能的前提

代码里**没有**「Qwen 超过 5 分钟就对不了」的硬上限：crate 的 GPU 预分配是
`MAX_TOKENS = 16384`（注释：~22 分钟音频），README 里有 50 分钟的用例。

真正的机制是：**现有管线从来不让对齐器见过超过 3 分钟的音频**——align 是逐 ASR 段
调用的，段长由 VAD + 分段时长约束在 30–180 s。限制一直没暴露，是因为 ASR 顺手
替它切了段。

**文稿匹配是第一条会把整段长音频交给对齐器的路径**（没有 ASR 来定义段）。CTC 的
单调 DP + `window=None` 整段一次对齐恰好是这条路径需要的东西，所以：

> **文稿匹配固定使用 CTC 对齐器**（产品规则，不是「默认」：整段一次对齐，块边界
> 不伤词）。设置里的 `[CTC] [Qwen]` 只管识别任务；文稿芯片的 hover 写明这一点。

## 2. 契约与不变式

> **文稿里的一行 = 生成字幕里的一条。**

文稿是文字的唯一来源，分行是边界的唯一来源，生成阶段不重新断句，只做长度兜底。

| 不变式 | 含义 | 怎么保证 |
|---|---|---|
| **机器不碰你的字** | 文稿任务全程只允许增删空白字符。全局「中文输出」设置对它**不生效** | `timeline::render` 的 `script` 由调用方给，文稿路径传 `TextScript::Original`；加测试断言非空白字符逐字不变 |
| **分行只有一个来源** | 界面上看到的断句就是生成结果 | 智能断句与生成时兜底**共用同一个长度预算**（`profile::source_char_limit`）。切分算法不同（无时间的贪心 vs 有时间的 DP），预算是同一处 |
| **不发明标点** | 沿用全代码库既有不变式 | 断行只在空白处切开，不插入任何非空白字符 |
| **token 不重不漏** | 文稿分行接进 `sentence_boundary` 的硬边界层，所有 token 恰好被分配一次 | 纯函数 + 断言 |

## 3. 交互

原则：**不加新任务类型、不加新页面、不加第二个开始按钮。** 一条任务就是一条任务，
区别只在于**它有没有挂文稿**。

### 3.1 信号归属

> **每个信号只出现在它所属的那个维度上。**

| 控件 | 只回答 |
|---|---|
| 状态胶囊 | 这条任务**到哪一步了**（待处理 / 处理中 / 完成） |
| 文稿芯片 | **有没有文稿**（识别是默认，不加标签） |
| 主按钮 | **现在能干什么**（▶ 开始 / 📁 打开） |

胶囊不承载任务类型。类型在两处自然可见：芯片在（**正信号**）；处理中阶段列表里
**没有「转写」这一项**（`转码 → 打轴 → 导出`）——这比静态标签准，因为它反映实际
发生了什么。

### 3.2 行的布局

沿用现有文法：左侧身份、右侧固定列控件簇。文稿芯片进控件簇，位置在**分离与 ▶
之间**——紧挨着它所改变的那个按钮，因果关系用相邻表达。

```
▎ ▶  【杂谈】分享下个人在字幕制作过程中使用AI语音识别   206MB · 20:51  1小时31分
     待处理   [中文▾]  [分离○]  [ +文稿 ]  [▶]  [🗑]
```

芯片是**一个按钮的两个状态**，`flex_shrink_0`，列宽固定
（`metrics.rs` 的 `TRANSCRIPT_COL_PX = 88.`），内容压到 `+文稿` / `文稿 3.2k ✎`——
行上不写「字」和 📄 图标（图标要解码、词不用，而且这一列放不下）。
名字行一个字不改；长名字照旧截断 + tooltip。

### 3.3 任务的四态

| 状态 | 状态胶囊 | 文稿芯片 | 主按钮 |
|---|---|---|---|
| 无文稿 | 待处理 | `[+文稿]` | ▶ 开始转写 |
| 有文稿 · 未跑 | 待处理 | `[文稿 3.2k ✎]` | ▶ 开始打轴 |
| 有文稿 · 跑过 · 文稿没改 | 完成 | `[文稿 3.2k ✎ ↻]` | 📁 打开 |
| 有文稿 · 跑过 · 文稿改了 | 完成 | `[文稿 3.2k ✎ ↻]` | **▶ 重新打轴** |

**一个开始按钮**，规则一句话：

> ▶ = 按这条任务当前的输入，把字幕做出来。有没有文稿决定要不要识别；跑没跑过
> 决定首次还是重跑（**重跑永远跳过识别**）。

第四行是重点：**文稿一改，任务就变回未完成**——输入变了，产物就不再对应当前输入。
主按钮自动从 📁 变回 ▶，这就是全部信号，**芯片不额外加标记**。这不是新机制，就是
现有 `done_with_out` 的自然延伸，和设置抽屉「脏了就亮保存」是同一条直觉。

### 3.4 添加：一处入口，两条路

**路径 A · 添加对话框（批量）**：一个对话框同时收**音视频 + 文本**，按文件名配对。

```
媒体（15 种）→ 建任务
文本（txt / srt / md）→ 找 stem 相同的媒体，找到就挂作文稿

配不上的文本 → 忽略，提示点名（"2 个文稿没有同名音视频：a.txt、b.txt"）
只有文本没媒体 → 不建任务，同样提示
```

- stem 比较**不区分大小写**，只比去扩展名的文件名
- 两个同名媒体 → 按选择顺序取第一个，并说明配给了谁
- 结果**必须在提示里说清**：配上了几个、配给谁、谁没配上

实现要点：

- rfd 多选一次只能选一种类型，所以要加一个**默认选中的「全部支持」过滤器**（媒体 ∪
  文本），混合多选才成立
- 对话框标题从「添加媒体」改成中性的「添加音视频与文稿」
- **拖拽路径走同一套配对**（空状态写的是「拖入音视频到此处」）。配对逻辑抽成纯
  函数，两条入口共用

**路径 B · 行上的「+文稿」**：打开文稿界面（§3.5）。覆盖「加的时候忘了带稿子」。

### 3.5 文稿卡片（悬停弹出，不是编辑器）

**鼠标停在芯片上就弹出来，移开自动收缩；点一下芯片把它粘住。** 机制照「用时」卡片
（悬停延时打开、移开有宽限期、卡片自己挂 `on_hover` 所以鼠标移上去不会关）。多一个
「粘住」是因为纯悬停的卡片上按按钮是难受的。

**没有文本输入框，也不做预览。** 本项目 vendored 的 gpui 0.2.2 不发布 `Editor`
组件（Zed 的编辑器是它自己另一个 crate 的产品代码，依赖 gpui 而不是相反），所以
「在应用里打字改文稿」目前做不到；硬写一个多行输入器意味着自己实现光标、选区、
撤销、剪贴板与 **IME 上屏**——中文输入法的坑全在最后一样上。

而且这与不变式一致：**程序永不写回用户的原文件**。所以卡片要显示的就是用户自己的
文件，整段铺回来只是让人重读一遍刚读过的东西。改文字的路径是「用顺手的编辑器改文件
→ 回来点重新读取」——这条路径不是妥协，它就是那条不变式的直接后果。

```
┌────────────────────────────────────┐
│ 杂谈分享.txt                         │
│ 47 行 · 3.2k字                       │
│ 约 5.1 字/秒 ✓  音频 26:31            │
│ 已忽略原时间轴，将重新打轴             │   ← 挂 .srt 时才有
│ ────────────────────────────────── │
│ [智能断句]  [重新读取]  [移除]        │
└────────────────────────────────────┘
```

三个动作：

- **智能断句** — 只拆过长的行，**只作用在暂存的那一份上**，原文件不动；行数当场变
  （`12 → 47 行`）。不预览切分结果：行数会变，字幕文件里就是结果。
- **重新读取** — 丢掉暂存上的改动，重新读一遍文件（只有来自文件的文稿才有这一项）。
- **移除** — 这条任务回到转录模式；已写出的产物不自动删。

**卡片只做三件只有它做得成的事**：呈现**解析之后**的摘要（SRT 的序号与时间轴已剥、
每个 cue 已合成一行）、密度校验、智能断句。

密度校验是防静默劣化的那道闸：文稿与音频对不上时，强制对齐**不报错**，它给一个
看起来正常但慢慢漂移的时间轴。所以这个数必须在**点开始之前**出现。

### 3.6 SRT 当文稿：解析只发生一次

```
选一个 .srt  →  剥掉序号与时间轴  →  一个 cue 的多行用 join_words 合成一行
                                     →  得到一段纯文本
                                         ↓
                          从此以后它就是一坨纯文本，和 .txt 没有区别
```

- **界面里不需要知道来源格式**：没有 SRT 模式，也没有「保留原时间轴」选项（不保留，
  头部一次性提示「已忽略原时间轴，将重新打轴」）
- **多行必须合成一行**：SRT 里的换行是**排版产物**（那个播放器、字号、边距算出来的
  换行），不是编辑决定。冻进文稿等于把一个字体相关的决定变成不可改的意图。合成用
  的是渲染 cue 时那条 `join_words`，前后一致
- 读入时处理 BOM / CRLF；只保留原始文件路径（用于「恢复原始内容」和输出重名判断）

### 3.7 输出重名保护

默认输出在源文件旁边，所以 `杂谈分享.mp4` + `杂谈分享.srt` 会让输出**覆盖用户原来
的字幕**。自动改名而不是拒绝：`杂谈分享.aligned.srt / .ass / .txt`，提示说清去了
哪。判断按**最终输出路径 vs 文稿路径**算，三种格式统一加后缀。

### 3.8 模型检查：任务级，不是全局级

现有全局 `align_ready` 问的是「**设置里选中的**对齐器就绪吗」，`settings.can_start()`
用它当闸门。放到文稿任务上会漏：

```
设置选了 [Qwen]、Qwen 已装  →  align_ready = true  →  闸门放行
但这条任务挂了文稿，要的是 CTC
CTC 没装                     →  跑到打轴阶段才炸
```

**用户看到的是「开始按钮能点，跑了 30 秒，然后失败」**，而缺模型是 3 秒就能知道的事。

所以闸门接任务自己的引擎：

```rust
if task.transcript.is_some() && !is_model_ready(ModelId::OmniAsrCtc300M) {
    flash_hint(/* 缺 CTC，去设置下载 */);
    return;   // 不入队
}
```

三处提示：

| 时机 | 形态 | 说什么 |
|---|---|---|
| 被动 | 文稿界面头部 | `· 需 CTC 对齐模型（设置里下载）` |
| 附上文本的当下 | 右下角状态栏 | 「已配对 xxx.txt」+（若缺）模型提示，一条说两件事 |
| 点开始 | 拦截，不入队 | 同上，措辞更硬 |

`is_model_ready` 与 `check_aligner_model_dir` 同一判据且自带缓存，**沿用
`refresh_model_probe` 现有的失效点**，不新增探针时机。

**批量开始**：缺模型的那几条**各自失败并提示，其余照常跑完**。不做全局拦截——用户
可能只想先跑那 20 条里的 15 条。

状态栏提示是 soft hint（几秒后自动消失），**放不下跳转按钮**，所以文案必须自带
指路。给状态栏加交互是独立决定，暂不做。

### 3.9 人声分离

一个字不改。它的语义自动变成「转写和对齐都用分离后的音频」——这正是这个功能需要
的：文稿打轴同样受益于去 BGM。

## 4. 管线

```
无文稿：convert → [分离] → VAD → ASR(分段) → 打轴(逐段) → 排版DP → 输出
有文稿：convert → [分离] → 读文稿 → 打轴(整段) → 文稿分行+兜底 → 输出
```

- 阶段标签：转码音频 → 加载对齐模型 → 对齐中 → 导出字幕（**没有「转写」**，
  这就是处理中判断任务类型的依据）
- 文稿分行接在 `sentence_boundary` 的**硬边界**层：文稿的行直接切 span，**跳过排版
  DP**，只留长度兜底
- 硬断言：所有 token 恰好被分配一次，不重不漏
- 产物与识别任务同名同目录；行「打开」仍指 srt

## 5. CLI

```powershell
oneasr-cli align --audio meeting.wav --text meeting.txt `
  --language zh --ass --chunk-seconds 60
# --line-breaks text|auto（默认 text）；--ass 追加逐字卡拉OK输出
```

与 GUI 同管线，先落地它——core 的两半（文稿解析 / 分行）可以脱离界面单测。

## 6. 明确不做

波形、音频播放、时间轴上的字幕编辑、翻译。功能边界就是**转录** 和 **文稿匹配**，
中间用 `↻` 串起来。**不引入 trait-per-stage、不引入插件注册**——8 步线性流程上
那是净亏，收益在契约不在架构。

## 7. 需要新建的东西

| 项 | 说明 |
|---|---|
| 文稿解析 | 纯函数：`(路径, 字节) → (纯文本, 来源元信息)`。txt/md 原样取行；srt 按 cue 合行 |
| 配对 | 纯函数：`(选中的路径[]) → (媒体[], 配对结果[])`。对话框与拖拽共用 |
| 行断 | `break_long_lines(text, limit)`：无时间的贪心切分，与排版 DP 共用预算 |
| 文稿分行 | 纯函数：`(词序列, 文稿行) → (行区间, token 归属)` |
| 管线入口 | `process_media_file_with_transcript(...)`，复用 `&dyn EngineProvider` |
| 浮层 | `overlays.rs` 加一种表面，遵守「同一时刻一个浮层」，与抽屉互斥 |
| 遮罩 | 这个 app 目前没有（抽屉是非模态覆盖，不需要） |
| 编辑器 | **本 app 第一个文本输入面**。gpui `Editor` 现成，IME 与撤销不用手写 |
| metrics | `TRANSCRIPT_W` / `TRANSCRIPT_MAX_H` / `TRANSCRIPT_COL_PX`，与既有列宽放一起 |
| 任务级检查 | 开始闸门接任务的引擎；provider 按任务构造（管线一行不用改） |

**依赖倒置正好接住最后一条**：管线持有 `&dyn EngineProvider`（`asr.rs`），所以
「这条任务用 CTC、那条用设置里的」只是构造不同的 provider，管线内部无需改动。
