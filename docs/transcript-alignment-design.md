# 「文稿对齐」功能设计 —— issues #2 / #14 的需求分析与 UI 交互方案

> 2026-10-06 · 输入：issue #2「希望增加文稿匹配功能」（已关，指向 CTC 对齐）、
> issue #14「希望增加 两个功能」（开放）。引擎侧：`docs/ctc-aligner-adoption-analysis.md`
> （CTC 对齐器已验证，与 Qwen 对齐器并存可选）。

## 1. 两个 issue 说了同一件事

| 来源 | 原话要点 | 需求本质 |
|---|---|---|
| #2 | 「类似剪映的文稿匹配：添加音频和与之对应的逐字稿（一行一句），给逐字稿自动打上时间戳，生成 srt 字幕。对于事先已有逐字稿的情况，就不用再做后续的字幕校队了」 | **音频 + 文稿 → 字幕**，跳过识别 |
| #14.3 | 「如果自己本身就是文稿，根本就不需要识别语音……自己使用文稿生成字幕文件，和剪映的文稿匹配类似。可以选择生成 srt（一行一个时间）和 ass（每个字都有时间）」 | 同上 + **ASS 逐字输出** |
| #14.2 | 「正确的步骤是识别出文字后可以修改校正，还有自己分行，然后再用 ForcedAligner 生成字幕——即没有错别字，也可以按自己的心意分行」 | **识别 → 人工校对 → 重对齐** 工作流 |
| #14.1 | 「希望能生成 ass 格式的、每个字有时间戳的字幕文件；srt 只能一句一个时间」 | ASS 逐字（卡拉OK）输出 |

四条诉求收敛为**一个新能力 + 两个输出增强**：

- 新任务类型：**对齐任务**（音频 + 文稿 → 时间轴 → 字幕），可完全跳过 ASR；
- 输出增强：**ASS 逐字卡拉 OK**（对齐/识别任务都可输出）；
- 工作流：**校对后重对齐**（把识别产出的文稿当作对齐任务的输入）。

现有 Qwen 对齐器做不了前两条的体验（两段式、歌声段失步，见采纳分析 §2.1），
CTC 对齐器的单调 DP + `inferred` 插值 + 内建 ASS 卡拉 OK 恰好补齐——
两个 issue 事实上是对齐器替换/并存的第二个论据。

## 2. 交互设计

原则：不新增页面，不改变「一个批量任务列表」的心智；对齐是任务的**一种模式**，
不是另一个 app。

### 2.1 添加对齐任务

- 现有「添加」按钮（rfd 文件对话框）旁新增次要动作 **「文稿对齐」**：
  ① 选音频（可多选）→ ② 选文稿（`.txt` / `.srt`，可多选，按文件名 stem 配对，
  数量不匹配时提示）。每对生成一行 mode=对齐 的任务。
  同 stem 的 `.srt` 导入时**剥掉原有时间轴只取文本**（用户可能拿旧字幕当文稿重对）。
- 不做 v1：系统级拖拽配对（gpui 外部文件拖放需额外工程），对话框路径已够用；
  未来加拖拽时行为保持一致。

### 2.2 任务行（对齐模式）

沿用现有行结构，新增三处：

```
[对齐] 会议录音.wav   wav · 12.4MB · 26:31     ← 类型徽标（识别行显示[识别]或维持现状）
  文稿: 会议录音.txt (3.2k字) ✎                ← 文稿 chip：点击可换文稿/预览前几行
  语言[中文▾]  断句[按文稿分行▾]  人声分离[  ]   ← 语言保留；断句下拉仅对齐行显示
  [开始] [删除]
```

- **类型徽标**：`[识别]` / `[对齐]`（Str 双语），一眼区分任务种类。
- **文稿 chip**：显示文件名与字数；`✎` 换文稿；hover 预览开头几行；文稿缺失（文件被删）
  时 chip 变红，开始时校验报错。
- **断句下拉**（仅对齐行，默认取设置）：
  - **按文稿分行**（默认，也是 #2/#14 的核心诉求）：文稿一行 = 一条字幕，时间 =
    该行首末 token；用户在文稿里决定分行，产品不复断。
  - **自动断句**：走现有 sentence_boundary（分段时长预设照旧生效）——适合整段无分行的大文稿。
- **语言**下拉保留：断句规则与 zh/yue 简繁转换仍需要；CTC 引擎本身不用语言参数（对用户无感）。
- **人声分离**开关保留：对齐同样受益于去 BGM（ sung 段实测 CTC 稳健，但分离更稳）。

### 2.3 输出

- 对齐任务产物与识别任务同名同目录：`{stem}.srt` / `{stem}.txt`；
  设置抽屉输出组新增 **「ASS 逐字（卡拉OK）」** 开关（默认关，双语标签），开启后额外写
  `{stem}.ass`——逐字 `\k` 时长直接取对齐 token（CJK 即逐字，拉丁文按词，ASS 惯例）。
  行「打开」仍指 srt；多产物进同目录。
- **不使用** ctc crate 自带的 SRT/ASS 断行（`views::build_cues`）——断句一致性归产品
  自己的 sentence_boundary / 文稿分行，crates 只供 token 时间。

### 2.4 校对 → 重对齐工作流（#14.2）

分两期，v1 先零新组件落地：

- **v1**：完成任务行新增动作 **「校对文稿后重对齐」**：
  1. 打开该任务导出的 `.txt`（或提示去输出目录）；
  2. 用户改正错字、按心意分行、另存；
  3. 右键该行 →「以此音频创建对齐任务」→ 选刚改好的文稿 → 新对齐行入列。
  提示语说明「按文稿分行」会让用户保留自己的分行。
- **v2**（独立立项，剪映式体验）：任务详情面板——左侧音频波形/播放 + 当前 cue 高亮，
  右侧文稿编辑，「生成字幕」就地重对齐。工程量大（音频播放、编辑器、状态同步），
  依 v1 反馈决定是否做。

### 2.5 对齐模型选择（与 ASR 0.6B/1.7B 同构）

- 设置抽屉「对齐模型」照「语音识别模型」的**分段按钮**样式（不做下拉）：
  `[Qwen] [CTC]` 两个按钮，选中态同 0.6B 的青色高亮；下方目录行跟随所选模型，
  各自记忆目录（照 ASR 每尺寸记目录的 `asr_dirs` 模式），目录选择/刷新按钮沿用现有
  `DLG_ALIGNER_DIR` 对话框。
- 下载列表新增 **omniASR-CTC-300M-v2**（1304MB fp32；ModelScope 已传好
  `eclipse005/omniASR-CTC-300M-v2`，走现有下载通道；可选补传 f16 变体省一半流量）。
- 对齐任务与识别任务的对齐阶段都使用所选对齐器；切换即时生效于下一个任务。
- 文案注明差异（双语）：CTC = 打轴更稳、支持语言广、无语言条件；Qwen = 与识别同源。
  yue/it/pt 精度待补测（见采纳分析 §5）。

### 2.6 CLI（issue #1 有人要命令行）

`oneasr-cli align` 子命令，与 GUI 同管线：

```powershell
oneasr-cli align --audio meeting.wav --text meeting.txt `
  --language zh --line-breaks text --ass --chunk-seconds 60
# --line-breaks text|auto（默认 text）；--ass 追加逐字卡拉 OK 输出
```

### 2.7 管线与阶段（core）

对齐任务的新入口（复用全部既有部件，跳过 VAD 与 ASR）：

```
convert(16k) → [可选人声分离] → align(文稿) → 断句(按文稿分行|自动) → SRT/TXT/ASS
```

- 阶段标签：转码音频 → 加载对齐模型 → 对齐中 → 导出字幕（新增/复用 i18n 键）。
- 「按文稿分行」= 输入文本按行切 span，token 按字符归属行，行首末 token 给时间——
  纯函数，好测。
- 进度、错误（文稿为空 / 音频过短 / 行数与音频时长明显不符时的警告）沿用 StageUpdate 通道。

## 3. 为什么这组设计能同时关掉两个 issue

- #2：v1 的「文稿对齐 + 按文稿分行 + SRT」= 剪映文稿匹配的最小完整体验。
- #14.3：同 v1；ASS 开关即 #14.1。
- #14.1：ASS 逐字输出，逐字时间来自对齐 token（CJK 逐字、拉丁按词）。
- #14.2：v1 的「校对后重对齐」闭环（无编辑器也成立），v2 再做编辑器。
